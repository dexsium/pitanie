# Импорт каталога продуктов в products_ru.db

Инструмент превращает **выгрузку, переданную владельцем данных** (CSV / JSON / JSONL / SQLite),
в оптимизированную SQLite-базу для приложения. Внешние сайты он **не опрашивает**.

## Почему здесь нет парсера perek.us

Проверено 4 ноября 2026 года:

- Публичный API (`/api/v1/foods/search`, `/foods/barcode/<code>`, `/foods/<brand>/<slug>`) требует ключ и
  в бесплатном тарифе даёт 500 запросов и **50 карточек продуктов в сутки**. Метода «список всех продуктов»
  нет, пагинации каталога нет.
- Страница разработчиков прямо указывает: массовая выгрузка не предлагается, каталог **нельзя собирать
  целиком, распространять или продавать как собственную базу**, ключи могут быть отозваны. Ключ нельзя
  встраивать в мобильное приложение. Бесплатный тариф — только для некоммерческих проектов.
- Оферта сервиса (п. 4.3) запрещает автоматизированный сбор данных без согласия оператора; `robots.txt`
  закрывает `/api/`.

Поэтому каталог встраивается в приложение только из выгрузки, на которую есть разрешение владельца.

### Что запросить у владельца

Письмо на адрес из раздела разработчиков (`ekinin.k@skybots.ru`, тема «API perek.us»):

> Здравствуйте! Мы разрабатываем бесплатное офлайн-приложение для учёта питания (код открыт, AGPLv3).
> Просим разрешение и выгрузку каталога продуктов со штрихкодами и КБЖУ (CSV/JSON/SQLite) для встраивания
> в приложение с указанием источника «Данные: perek.us». Готовы согласовать условия, срок и порядок
> обновлений. Если массовая выгрузка невозможна, просим сообщить, допустим ли онлайн-поиск по штрихкоду
> через ваш сервер/ключ в качестве запасного варианта.

Приложение не встраивает данные, пока нет письменного разрешения.

## Использование

```bash
python main.py --input export.csv --output products_ru.db \
    --source "perek.us (выгрузка владельца)" --catalog-version 2026.11.1 \
    --map name=Название --map barcode=Штрихкод --map calories=Ккал
```

- Без `--map` ожидаются колонки с именами полей: `source_id, barcode, name, brand, manufacturer,
  category, calories, proteins, fats, carbohydrates, serving_size, package_weight, nutrition_basis,
  updated_at`.
- `--per-serving` — КБЖУ во входном файле даны на порцию (пересчёт на 100 г/мл только при известной
  массе порции, иначе значения остаются пустыми).
- Результат: `products_ru.db`, `products_ru.db.sha256`, `products_ru_report.json`.

## Что делает

- Штрихкоды хранятся как TEXT. Канонический вид: EAN-8 или EAN-13 (UPC-A получает ведущий 0), все формы
  кода лежат в `product_barcodes`, поэтому поиск находит товар и по UPC-A, и по EAN-13.
- Контрольная сумма GS1 проверяется; продукт с плохим кодом не удаляется, код становится NULL.
- КБЖУ приводится к 100 г / 100 мл; пусто остаётся NULL; отрицательные и невозможные значения обнуляются
  (NULL) с записью в отчёт. Расхождение с 4/9/4 продукт не отбраковывает.
- Дубли: один канонический штрихкод (остаётся более полная запись) либо полное совпадение полей для
  записей без кода. Одинаковые названия разных производителей сохраняются.
- FTS5 по названию, марке и производителю (`products_fts`), индексы по штрихкоду, названию и марке,
  таблица `meta` (версия схемы и каталога, дата, статистика), контрольная сумма файла.
- В отчёте нет утверждения о полноте каталога: она определяется только входной выгрузкой.

## Сборка приложения (после получения данных)

1. Выполнить импорт, положить `products_ru.db` в `assets/database/`.
2. Добавить файл в `pubspec.yaml` (`assets:`), поднять версию и записать в CHANGELOG.
3. Подключение к существующему каталогу и сканеру — отдельный этап; пользовательские продукты остаются в
   БД приложения и каталогом не затрагиваются.
